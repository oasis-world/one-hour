# 修复多游戏卡片滚动抖动（Supabase 重连 + 底部按钮高度）—— 实施计划

**背景回顾：** 上一轮已将占位 `→` 实卡的高度差从 `~140px` 缩至 `~10-20px` 并将 `ResizeObserver` 的同步 `scrollTop` 写入合并为单帧 `rAF`、隔离毛玻璃采样，首屏抖动明显改善。剩余抖动在“多个卡片同时在列表中上下滚动”时仍可复现，用户怀疑与 **卡片进出视界时的卸载/重建 + Supabase Realtime 重连** 以及 **底部按钮/状态文案的显隐** 相关。三个 Explore 子任务已验证该假设。

---

## 一、已验证的根因（带行号）

### 1) 进出视界即卸载 → 重连风暴
* `GameMessage.tsx:18 + 54-79 + 102-158` 的双机制（`IntersectionObserver rootMargin 360px` + `measureVisibility` 精确矩形裁剪）是 **唯一能将 `isInView` 置回 `false` 的路径**，一旦置 `false`，`{active ? <Component/> : <Placeholder/>}:152-158` 会 **完全卸载** `ChessGame / GomokuGame / XiangqiGame` 的 React 树，触发其 `useEffect` 清理：
  * `chess:182-224` 直接 `removeChannel`，无重试、无 slot、无 `watchGameChannelClose`；
  * `gomoku:265-643` / `xiangqi:426-796` 走 `acquireGameChannelSlot (MAX_ACTIVE_GAME_CHANNELS=2):realtime.ts:66-113` → `removeStaleGameChannel` → `channel.subscribe` → `channel.track` (8s 超时) → `load*State` DB 异步拉取 → `state-request` 轮询。每穿越一次 360px 边距就完整复跑一次，`players / status / joinStatus` 在空态与水合态间闪烁。
* 内存态（`stateRef / selected / legalTargets / boardStyle / profileLooks / joinStatus / toast timers / aiTimerRef / aiWorker`）全部丢失，重建时先渲染 `useState(() => createInitialState(instanceId, hostId))` 的空阵容 `players:[]` → 从 `cloudState.ts:5-21` 异步水合才回到真实 `players/status/winner`。这段时间卡片高度会经历 `空玩家区 (0→55px) + 空结果条 (0→28px) + 棋盘空→实` 多次跳变，每次都命中 `GameMessage.tsx:102-123` 的 `heightDelta>0.5` 补偿路径，贴底时又与 `useChatScroll.ts:136-153` 的 `MutationObserver → pin` 争夺，最终表现为“拉锯抖动”。
* 额外：`Gomoku` / `Xiangqi` 有 2 槽位信号量，`Chess` 无；多卡同时滚动时第三个卡在 `acquireGameChannelSlot` 处排队等待，状态更不确定。

### 2) 卡片内部“内容决定高度”导致滚动中二次跳变
* **玩家区：** `chess:335` `players.length>0 && <div>` 完全移除；`gomoku:883 / xiangqi:1014` 虽常驻容器但 0 子项时仍含 `margin:14px 0 11px`，`0→1→2` 人各 `~55px`。`ChessGame.css:5 / Gomoku.css:105 / Xiangqi.css:100` 均无 `min-height` 预留。
* **结果条：** `status==='result' && <div class="*-result">:chess:344 / gomoku:914 / xiangqi:1039` 在 `waiting→playing→result` 间 `0↔28px`，且 `statusHint` (`waiting/Your turn/Waiting for opponent` vs `result→''`) 同步使 `*.head .*.status` 与 `*.meta .dot` 消失（`chess:323 / gomoku:844 / xiangqi:991`）。
* **底部操作栏：** 派生谓词 `canJoin / canJoinAI / canRestart / canLeave` (`chess:252-259 / gomoku:805-817 / xiangqi:962-971`) 决定 `*.actions:chess:10 / gomoku:325 / xiangqi:575` 内 `0/1/2 × .btn-accent{44px}` 的增删，空时仅剩 `margin-top:8-11px`。`channelReady` (`ready:chess:53 / readyChannelKey:gomoku:91 / readyKey:xiangqi:106`) 仅改按钮文案/禁用，但 `joinStatus: idle→joining→retry` 的长文案 `“加入较慢，点击重试”` 会改变宽度进而可能换行。所有这些都在 `playing` 中反复发生（AI 加入、人加入、`result`），且发生在列表中段——此时 `GameMessage` 的 `lastBottom <= rootTop` 补偿正活跃，极易与滚动冲突。
* **Toast：** `winnerToast/startToast/captureToast` 均为棋盘内 `position:absolute`，不占流；`AiThinkingTimer` 已在上一轮用 `min-width` 定宽，独留宽度截断，无高度抖动——非主因。

### 3) 滚动锚定“双重补偿”
* `GameMessage.css:70-79` 已将 `chat-log {overflow-anchor:none}` 并把锚点交 `GameMessage` 的 `rAF queueDelta`，但 `useChatScroll.ts:116-153` 的 `ResizeObserver(container) → scrollTo(bottom)` 与 `MutationObserver(subtree+characterData) → pin` 仍会在贴底时对同一 `heightDelta` 再做一次 `scrollTop = scrollHeight`。对视口上方的高度变化这是竞争；对贴底读者这是正确行为。当前 `isAtBottom` 守卫 (`dist<=56`) 已缓解，但当多个离屏卡因 `channelReady` 翻转或 `players` 水合而连环增高时，批处理窗口外的第二帧仍会产生二次修正。

## 二、总体思路

将 **“是否渲染”** 与 **“是否联网”** 解耦：
* 渲染层：首见即常驻（`hasEverBeenVisible` 保活），不再用占位替换实卡；离屏仅靠 `content-visibility:auto` 跳过绘制，不再产生高度差。
* 联网层：离屏时暂停 Supabase 订阅但保留内存 `state`，回视时复用内存态并做一次追赶，不再经历 `createInitialState → 空闪`。
* 布局层：对玩家区/结果条/操作栏预留最小高度，消除 `0↔N` 的文档流跳变；剩余不可避免的高度变化改由 CSS `interpolate-size` / 固定时长过渡平滑，而非瞬时跳变。

## 三、详细实施步骤

### Step 1 — `GameMessage` 保活（不再二次占位）
* **文件：** `src/games/GameMessage.tsx` (~160→~170 行，需拆 `useGameVisibility` 子 hook 以守 200 行)
* 新增 `const [hasEverMounted, setHasEverMounted] = useState(initiallyVisible)`；`isInView` 变 `true` 时 `setHasEverMounted(true)`，永不置回 `false`。
* 渲染改为：
  ```tsx
  {hasEverMounted ? (
    <div className={`game-card-keepalive ${isInView?'is-inview':''}`}>
      <Component isVisible={isInView} ... />
    </div>
  ) : <Placeholder type={...} />}
  ```
  `is-inview` 仅控制 `content-visibility`，不控制挂载。`Placeholder` 仅首现前出现一次，其 `→` 实卡的 `heightDelta` 仍走现有 `queueDelta` 补偿，但之后永不再发生。
* `GameMessage.css` 新增 `.game-card-keepalive:not(.is-inview) { content-visibility:auto; contain-intrinsic-size: 540px 540px; }` 与 `.chat-log { overflow-anchor:none }` 保持不变。首屏 `initiallyVisible` 卡直接 `hasEverMounted=true` 不闪。
* **风险：** 常驻 DOM 增加节点数；缓解：`content-visibility:auto` 已让离屏卡跳过绘制与布局，实测 10 卡内可接受。

### Step 2 — 游戏组件“可视即联网”改造
* **文件：** `src/games/chess/ChessGame.tsx`、`gomoku/GomokuGame.tsx`、`xiangqi/XiangqiGame.tsx` + `src/games/realtime.ts`
* 为三者新增可选 prop `isVisible?: boolean`（默认 `true` 兼容旧调用）。
* 将现有“挂载即建连” `useEffect([instanceId,selfId,hostUserId])` 拆为两段：
  1. **状态保活段**（始终存活）：`useState(createInitialState)` 改为 `useRef` + `useState` 的惰性水合，仅在 `load*State` 成功后 `setState`，此后永不重置为 `createInitialState`。
  2. **连接段** `useEffect([isVisible, instanceId, selfId, channelKey])`：`!isVisible` 时 `unsubscribe(1500)+teardown+releaseSlot` 但 **不清空 `state`**；`isVisible` 回真时复走 `removeStale→acquireSlot→subscribe→track→loadOrRequest`，但若 `stateRef.current.players.length>0` 则跳过 `createInitialState` 的空闪，直接复用内存态并发送 `state-request` 追赶。
* 统一 `Chess` 也走 `acquireGameChannelSlot` 与 `watchGameChannelClose`（`realtime.ts` 已有，`chess` 之前遗漏），`MAX_ACTIVE_GAME_CHANNELS` 视保活后的并发提升至 `3` 或改为“可视卡优先、离屏卡排队”的 LRU（简单方案：离屏卡的 `acquire` 在 `isVisible===false` 时主动 `releaseSlot` 让出槽位）。
* `persistQueueRef` 与 `scheduleAiTurn` 仅在 `channelReady && isVisible` 时触发，避免离屏 host 误写。
* **文件规模控制：** 三个 `*Game.tsx` 均远超 200 行（`Gomoku` ~643、`Xiangqi` ~796），借此机会将连接逻辑抽至 `src/games/useGameChannel.ts` (≈120 行) 与 `src/games/useGamePresence.ts`，主组件仅保留渲染与手势。

### Step 3 — 卡片内部高度预留（消除内容跳变）
* **文件：** `src/games/chess/ChessGame.css`、`gomoku/GomokuGame.css`、`xiangqi/XiangqiGame.css`（各追加 <10 行，保持 <200 行或拆 `GameCardLayout.css`）
* ```css
  .chess-players, .gomoku-players, .xiangqi-players { min-height: 42px; } /* 空阵容时保留 1 行高度 */
  .chess-result, .gomoku-result, .xiangqi-result { min-height: 22px; }
  .chess-result:empty, .gomoku-result:empty, .xiangqi-result:empty { visibility: hidden; } /* 用 visibility 而非 display:none */
  .chess-actions, .gomoku-actions, .xiangqi-actions { min-height: 44px; align-items: center; }
  .chess-actions:empty, .gomoku-actions:empty { visibility: hidden; min-height: 44px; } /* 观战 playing 空栏不塌陷 */
  ```
* 对应的 `tsx` 将 `{status==='result' && <div class="*-result">}` 改为常驻 `<div class="*-result" aria-live="polite">{status==='result'? text : ''}</div>`；`players` 区亦常驻，仅内部 `map` 为空；`actions` 区同理常驻空容器。高度变化从 `0↔N` 变为 `预留↔N`，`ResizeObserver` 感知到的 `heightDelta` 从 `28-88px` 降至 `0-10px`。观战空栏会多 `~36px` 空白，需与设计确认是否可接受（见下方提问）。
* 可选平滑：对上述容器加 `transition: min-height 180ms ease` + `interpolate-size: allow-keywords`（受控于 `prefers-reduced-motion`），使不可避免的 `waiting→playing→result` 高度变化平滑而非瞬时。

### Step 4 — 滚动锚定收敛
* **文件：** `src/games/GameMessage.tsx` + `src/components/useChatScroll.ts`
* `GameMessage` 的 `queueDelta` 已具备 `isAtBottom` 守卫，Step 1 后该路径仅在首现与三处预留外的剩余跳变时触发，频次大幅下降；无需改动，仅保留 `pendingDelta` 聚合。
* `useChatScroll.ts:136-153` 的 `MutationObserver(characterData:true)` 会捕获 `AiThinkingTimer` 的每秒 `0s→1s` 文本变化，若此时贴底会每秒 `scrollTo(bottom)`——虽正确但与 `GameMessage` 的 `characters` 无关，应加过滤：`mutation.target.closest('.game-ai-thinking-wrap')` 则跳过。或将 `characterData` 观测范围缩至 `childList` 仅对图片/新消息生效。
* 验证 `savedListPosition` 的 `atBottom` 阈值 `56px` 与本方案一致，避免阈值不一致导致的“临界抖动”。

### Step 5 — 验证与回退
* 本地复现：构造含 5-6 个 `__GAME__` 的历史（`chess/gomoku/xiangqi` 混合，含 `waiting/playing/result` 各态），中速上下滚动 + 观察者 DevTools Performance 录制，确认 `scrollTop` 写入次数由每卡一次降至首现一次，Channels 数由 `N` 波动收敛至 `visibleCount (≤2-3)`。
* Supabase 侧：控制台 Realtime Inspector 确认离屏卡 `unsubscribe` 后 `activeGameChannels` 计数回落，无泄漏 `stale topic`。
* `npm run build && npm run lint` 必须通过；三处 `GameMessage.css` 预留高度需在浅色/深色主题与 `max-width:600px` 断点下均目视检查。

## 四、权衡与风险

| 维度 | 旧方案（卸载重建） | 新方案（保活+联网分离） | 取舍 |
|---|---|---|---|
| 滚动平稳度 | 每次穿越 360px 即 `heightDelta` + 空闪 + 按钮重排 | 首现一次 `heightDelta`，后仅预留高度内的微调 | 显著提升 |
| 内存/绘制 | 离屏零成本 | 离屏 DOM 常驻但 `content-visibility:auto` 跳过绘制，内存 +~3×卡片 | 可接受（上限 ~10 卡） |
| Realtime 负载 | N 卡同时建连可能超限但瞬时 | 可视卡常连 + 离屏暂停，峰值可控；需 `MAX_ACTIVE 2→3` | 需监控 |
| 空栏空白 | 观战 playing 时操作栏塌陷省空间 | 预留 44px 空白，视觉略空 | 需设计确认 |
| 实现风险 | 无 | 需改三套 `*Game.tsx` 的连接生命周期，`Chess` 补 slot | 中等，需拆 hook |

*回退预案：* 若 Step 2 的按需联网引入回归，可独立回退 Step 2 而保留 Step 1+3——保活渲染已能消除大部分空闪抖动。
